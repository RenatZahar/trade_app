# Программа доведения до уровня Junior+ (фокус: AI agents / agentic systems)

## Цели и приоритеты

- **P0:** воспроизводимость пайплайна (run + config + logs).
- **P1:** инженерное качество (структура, читаемость, ошибки, тесты).
- **P2:** оптимизации и продвинутые темы (фиксируем как backlog, без главного фокуса).

## Формат обучения (итерации)

Каждая итерация = одна тема:
1. Короткая теория (15–25 минут).
2. Минимальная интеграция в проект (30–90 минут).
3. Ревью и фиксация артефакта в репозитории.
4. DoD + чеклист junior+ компетенции по теме.

## Роль ассистента в этой программе

В рамках этой программы ассистент выступает **в двух ролях одновременно**:

- **Инженерный напарник**: читает код, находит риски, предлагает изменения, помогает доводить итерацию до инженерного результата. Не вносит изменения в файлы, если пользователь не просит обратного.
- **Учитель**: объясняет незнакомые темы перед практикой, дает краткую теоретическую базу, связывает изменения в коде с инженерными принципами.

### Баланс работы: 50/50

Для **каждой итерации** действует жесткое правило баланса:

- около **50% внимания** уходит на понимание темы, причин решений и инженерного контекста;
- около **50% внимания** уходит на практическую работу в проекте: анализ, правки кода, проверку результата, фиксацию артефактов.

Это не означает формальный подсчет минут, но означает, что итерация не должна скатываться:

- либо в “сухую теорию” без реального изменения проекта;
- либо в “молчащее кодирование” без объяснения причин и контекста.

### Правило новых тем

Если в текущей итерации затрагивается тема, которую пользователь еще не знает или не проходил в проекте, сначала делается **краткое теоретическое объяснение**, и только потом предлагаются или выполняются изменения в коде.

Формат объяснения:

- кратко и по делу;
- только в объеме, достаточном для продолжения работы;
- с привязкой к текущему проекту, а не как абстрактная лекция.

### Проверка достаточности понимания

Ассистент должен делать короткую проверку понимания **не для оценки знаний пользователя**, а чтобы выбрать следующий шаг:

- можно ли сразу переходить к изменениям в коде;
- или сначала нужна еще минимальная теоретическая база.

Если у пользователя остаются вопросы глубже этого минимума, он задает их отдельно.

### Формат взаимодействия

Основной режим работы в программе:

- краткое объяснение;
- совместная работа над проектом;
- возврат к теории только тогда, когда это нужно для осмысленного продолжения.

Обязательные упражнения, домашние задания и отдельные учебные мини-практикумы по умолчанию не требуются.

## Дорожная карта (13 итераций)

### 1) Reproducible run: единая точка запуска и профили окружения (P0)
**Junior+ умеет:** запускать проект одинаково на любой машине по инструкции и конфигам.

- Что внедряем:
  - `run`-скрипт/команда для основных сценариев (`train`, `update_data`, `serve`).
  - проверка обязательных переменных окружения на старте.
  - фиксированная структура runtime-логов.

### 2) Конфигурация без “магии” (P0/P1)
**Junior+ умеет:** держать конфиг централизованно и валидировать его.

- Что внедряем:
  - `settings` слой (валидация, default values, явные ошибки).
  - разделение runtime-конфига и экспериментального ML-конфига.

### 3) Логирование и наблюдаемость пайплайна (P0)
**Junior+ умеет:** быстро локализовать падение и восстановить контекст запуска.

- Что внедряем:
  - единый формат логов (module, stage, run_id, duration, status).
  - логирование старта/финиша ключевых шагов (data → features → train → evaluate).

### 4) Ошибки и контракты модулей (P1)
**Junior+ умеет:** делать предсказуемую обработку ошибок и не скрывать сбои.

- Что внедряем:
  - явные exception-классы/категории.
  - fail-fast на невалидных входах.
  - отказ от `print` в критичных местах в пользу логгера.

### 5) Тестовый фундамент (P1)
**Junior+ умеет:** покрывать критичный happy path и ключевые edge-cases.

- Что внедряем:
  - базовый `pytest`-контур и 1–3 smoke/unit теста на P0-часть.
  - фикстуры для минимальных мок-данных.

### 6) Детерминизм и контроль эксперимента (P0/P1)
**Junior+ умеет:** повторять результаты обучения при одинаковых входах.

- Что внедряем:
  - фиксация random seeds.
  - сохранение метаданных запуска (commit hash, параметры, версия данных).

### 7) Границы ответственности модулей (P1)
**Junior+ умеет:** отделять orchestration от бизнес-логики и I/O.

- Что внедряем:
  - “тонкий” orchestrator, “толстые” pure-функции.
  - минимизация циклических импортов.

### 8) Минимальный quality gate в CI (P1)
**Junior+ умеет:** предотвращать регрессии до merge.

- Что внедряем:
  - минимальный GitHub Actions gate вокруг `python -m pytest tests/unit_smoke -q`;
  - fail при падении быстрых smoke/unit checks;
  - lint всего проекта не включается в обязательный gate на старте и переносится
    в технический backlog 13-й итерации.

### 9) Agentic-ready контуры (P2, на будущее)
**Junior+ умеет:** проектировать функции так, чтобы ими мог управлять агент.

- Что внедряем:
  - idempotent actions.
  - machine-readable outputs (JSON-сводки шагов).
  - строгие input/output контракты инструментов.

### 10) Портфолио упаковка (P1)
**Junior+ умеет:** показывать проект как инженерный продукт.

- Что внедряем:
  - README: architecture, quickstart, known limits.
  - примеры запусков + sample logs + roadmap.


### 11) Ревизия и гигиена документации заметок (P1)
**Junior+ умеет:** поддерживать рабочие заметки в актуальном и пригодном для ревью состоянии.

- Что внедряем:
  - единый формат заметок в `docs/` (цель, контекст, решения, next steps).
  - регулярный обзор заметок: удаление устаревшего, фиксация статуса задач.
  - связь заметок с кодом: ссылки на затронутые модули и сценарии запуска.

### 12) Повтор теоретических знаний и проверка понимания (P1)
**Junior+ умеет:** объяснять уже внедренные инженерные решения и применять теорию к своему проекту.

- Что внедряем:
  - отдельный промт проверки знаний;
  - вопросы по Git, Python runtime, CLI, logging, tests, SQL и детерминизму;
  - проверку, что технически завершенная итерация действительно соответствует
    заявленной компетенции "Junior+ умеет", а не только закрытому чеклисту;
  - фиксацию учебных хвостов по Python-механике, если они всплыли в итерациях:
    `raise`, propagation исключений, `*args`, `**kwargs`, сигнатуры функций;
  - фиксацию пробелов и коротких next steps перед следующими крупными задачами.

### 13) Технический долг и следующие направления развития (P2, после технической шлифовки)
**Junior+ умеет:** превращать разрозненные технические хвосты в проверяемый backlog и планировать развитие проекта без потери воспроизводимости.

- Что внедряем:
  - адаптацию логики старого Jupyter notebook к runtime-формату приложения;
  - отдельный тестовый сценарий сравнения `app pipeline` vs `legacy notebook pipeline`;
  - вероятно, декоратор или аналогичный instrumentation-layer для сохранения результатов ключевых функций в файлы;
  - единый формат артефактов для последующего diff/сопоставления между основным и тестовым пайплайном.
  - ревизию модели `data_table` + `few_tx_wallets` и возможный переход к
    `wallet_stats` / service-таблицам;
  - решение по `data/block_height_block_time_map/map.parquet`: оставить parquet
    cache, перенести в SQLite/service-таблицу, пересчитывать из `data_table` или
    заменить lookup-слоем;
  - DB schema contract для новых SQL-таблиц: сценарии указывают зависимые
    таблицы, smoke проверяет покрытие контрактом, live DB drift подсвечивается
    warning-only;
  - ревизию старых сценариев запуска из `main.py` и technical debt comments из
    `runtime_scenarios.py`;
  - решение по месту repo tooling/scripts, включая
    `scripts/update_requirements_lock.py`;
  - решение по public/private boundary: demo-заглушка, private package/core repo
    или другой честный формат разделения strategy logic и public infrastructure;
  - постепенное введение lint без обязательного lint всего проекта на старте.

## Почему это подходит именно вашему проекту

Текущее состояние проекта указывает, что **первый фокус должен быть P0/P1**, а не оптимизации модели:

- В `main.py` много флагов запуска, ручных переключателей и смешение тестового/боевого сценария.
- В `main_functions.py` есть смесь orchestration + инфраструктуры + побочных эффектов.
- Есть точечные тесты в `modules/tests`, но отсутствует единый тестовый каркас вокруг P0-цепочки.

Это повышает риск “модель не сходится” из-за неуправляемых различий запуска, а не только из-за ML-гиперпараметров.

## Шаблон одной итерации (как будем работать)

1. Выбираем тему (из roadmap выше).
2. Фиксируем список затронутых тем по итерации.
3. Если среди них есть новая тема, сначала дается короткое теоретическое объяснение, затем коротко проверяется, достаточно ли базы для перехода к практике.
4. Я даю 2–3 участка кода-кандидата + вариант “выберите сами файлы”.
5. Делаю диагноз (3–7 рисков с метками P0/P1/P2).
6. Предлагаю 3 варианта вмешательства:
   - **Minimal patch** (быстро, безопасно),
   - **Medium refactor**,
   - **Rewrite slice** (локальное переписывание).
7. Вы выбираете вариант.
8. Делаем изменения + фиксируем портфолио-артефакт.
9. Добавляем **Industry note (de-facto alternatives)**:
   - 1 альтернативная распространенная практика,
   - почему в этой итерации выбран текущий вариант,
   - мини-пример альтернативы (2–6 строк кода/команды).

### Протокол начала новой итерации

Перед стартом новой итерации обязательно пройти короткий чеклист:

1. Проверить текущую ветку:
   - `git branch --show-current`
2. Проверить, что рабочая ветка предыдущей итерации запушена на `origin`.
3. Проверить, что предыдущая итерация слита в `main_branch`:
   - локально;
   - и на удаленном репозитории.
4. Если ветка предыдущей итерации не слита в `main_branch`, сначала завершить merge/sync, и только потом начинать новую итерацию.
5. Создать отдельную ветку под новую итерацию от актуального `main_branch`.
6. Сразу запушить новую ветку на GitHub, чтобы дальнейшая работа велась уже в правильном контексте.
7. Проверить наличие и актуальность файлов в `docs/`, особенно:
   - `docs/junior_plus_program.md`
   - `docs/iterations/iteration_<N>.md` для прошлых итераций
8. Перед практикой коротко зафиксировать:
   - тему итерации;
   - цель;
   - хвосты с прошлой итерации, если они реально переходят дальше.

Дополнение к протоколу:

- Если хвост прошлой итерации относится не к основному результату итерации, а к локальной шлифовке конкретных модулей, он может быть перенесен дальше без блокировки новой итерации.
- Такой перенос нужно фиксировать явно:
  - в файле завершенной итерации;
  - в стартовом файле новой итерации, если хвост влияет на контекст решений.

## Межчатовый протокол работы (чат-оркестратор + чаты-итерации)

Да, этот документ можно использовать как **единый ориентир между чатами**.

- **Чат-оркестратор (этот):**
  - поддерживает roadmap,
  - фиксирует решения по приоритетам,
  - обновляет статус итераций,
  - хранит правила взаимодействия и DoD-шаблоны.
- **Чат-итерация (новый чат под тему):**
  - выполняет конкретную тему,
  - делает диагноз по выбранным файлам,
  - предлагает 2–3 варианта вмешательства,
  - вносит минимальные изменения в код.

### Что сохраняется между чатами

- История конкретного чата в новый чат **не переносится автоматически**.
- Но содержимое репозитория доступно из любого нового чата, поэтому
  `docs/junior_plus_program.md` можно использовать как «контракт процесса».

### Где хранить заметки по итерациям

Рекомендуемый подход:

1. В этом файле хранить **только**:
   - общую программу,
   - статусы по итерациям,
   - правила процесса.
2. Для каждой итерации заводить отдельный файл:
   - `docs/iterations/iteration_01.md`, `iteration_02.md`, ...
   - внутри: цель, список затронутых тем, диагноз, выбранный вариант (minimal/medium/rewrite), DoD, результат, что дальше.

Это уменьшает «кашу» и дает чистый портфолио-след по эволюции проекта.

```md

- Альтернатива (de-facto): `<подход>`

  ```

- Почему не берем сейчас: ниже порог входа для первой итерации
- Мини-пример:
  ```bash
  py main.py train
  py main.py serve
  ```
```

## Критерий прогресса до Junior+

К концу программы должны выполняться критерии:

- Проект запускается по документированному сценарию без ручного “тыканья” флагов.
- Любой запуск оставляет диагностируемый след (логи + конфиг + run metadata).
- Базовые P0-сценарии покрыты автотестами.
- Ошибки классифицированы, падения не “проглатываются”.
- Архитектура модулей понятна и объяснима на собеседовании.

## Практика синхронизации между чатами (Git)

Если новый чат «не видит» файл из текущего, почти всегда причина в разной ветке/контейнере.

Минимальный стартовый чек в новом чате:

```bash
pwd
git branch --show-current
git log --oneline -n 5
rg --files | rg 'docs/junior_plus_program\.md'
```

> Примечание: этот файл — про учебную программу. Детали разовой настройки Git/SSH специально не держим здесь, чтобы не размывать фокус.


### Рабочий протокол веток (договор)

- Базовая стабильная ветка: `main_branch`.
- Рабочая ветка текущей итерации: `feature/iteration-01-cli` (долгоживущая на время итерации).
- Временные ветки `codex/*` не используем как основное место разработки; после завершения работы их удаляем локально и на `origin`.

Рекомендуемый цикл:

```bash
git switch main_branch
git pull
git switch feature/iteration-01-cli
git pull
# работа, коммиты
git push
```

Завершение итерации:

```bash
# локально, до финального push
python -m pytest tests\unit_smoke -q
git switch main_branch
git pull
git merge --no-ff feature/iteration-01-cli
git push
```

После финального `git push` обязательно проверить GitHub Actions workflow
`Quality Gate` на том commit, который ушел в `main_branch`.

Смысл проверки:

- локальный smoke-прогон быстро ловит ошибки до commit/push;
- GitHub Quality Gate запускает ту же базовую команду
  `python -m pytest tests/unit_smoke -q`, но в чистом GitHub checkout с
  установкой зависимостей заново;
- после push не нужно блокировать дальнейшие короткие рабочие действия
  ожиданием GitHub Actions; можно продолжать работу и вернуться к проверке
  результата примерно через 4 минуты;
- итерация считается закрытой только после зеленого локального smoke и зеленого
  GitHub Quality Gate на финальном pushed commit;
- если GitHub Quality Gate падает, нужно внести fix-коммит, снова push и снова
  дождаться зеленого run.

### Быстрый протокол безопасной синхронизации (если есть локальные правки и ветка behind)

```bash
git stash push -u -m "wip before sync"
git pull --rebase origin <branch>
git stash pop
```

После `stash pop` обязательно проверить `git status` и разрешить конфликты, если они появились.
