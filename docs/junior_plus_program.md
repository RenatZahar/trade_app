# Программа доведения до уровня Junior+ (фокус: AI agents / agentic systems)

## Цели и приоритеты

- **P0:** воспроизводимость пайплайна (run + config + logs).
- **P1:** инженерное качество (структура, читаемость, ошибки, тесты).
- **P2:** оптимизации и продвинутые темы (фиксируем как backlog, без главного фокуса).

## Формат обучения (итерации)

Каждая итерация = одна тема:
1. Короткая теория (15–25 минут).
2. Минимальная интеграция в проект (30–90 минут).
3. Ревью и фиксация артефакта в репозитории.
4. DoD + чеклист junior+ компетенции по теме.

---

## Дорожная карта (11 итераций)

### 1) Reproducible run: единая точка запуска и профили окружения (P0)
**Junior+ умеет:** запускать проект одинаково на любой машине по инструкции и конфигам.

- Что внедряем:
  - `run`-скрипт/команда для основных сценариев (`train`, `update_data`, `serve`).
  - проверка обязательных переменных окружения на старте.
  - фиксированная структура runtime-логов.

### 2) Конфигурация без “магии” (P0/P1)
**Junior+ умеет:** держать конфиг централизованно и валидировать его.

- Что внедряем:
  - `settings` слой (валидация, default values, явные ошибки).
  - разделение runtime-конфига и экспериментального ML-конфига.

### 3) Логирование и наблюдаемость пайплайна (P0)
**Junior+ умеет:** быстро локализовать падение и восстановить контекст запуска.

- Что внедряем:
  - единый формат логов (module, stage, run_id, duration, status).
  - логирование старта/финиша ключевых шагов (data → features → train → evaluate).

### 4) Ошибки и контракты модулей (P1)
**Junior+ умеет:** делать предсказуемую обработку ошибок и не скрывать сбои.

- Что внедряем:
  - явные exception-классы/категории.
  - fail-fast на невалидных входах.
  - отказ от `print` в критичных местах в пользу логгера.

### 5) Тестовый фундамент (P1)
**Junior+ умеет:** покрывать критичный happy path и ключевые edge-cases.

- Что внедряем:
  - базовый `pytest`-контур и 1–3 smoke/unit теста на P0-часть.
  - фикстуры для минимальных мок-данных.

### 6) Детерминизм и контроль эксперимента (P0/P1)
**Junior+ умеет:** повторять результаты обучения при одинаковых входах.

- Что внедряем:
  - фиксация random seeds.
  - сохранение метаданных запуска (commit hash, параметры, версия данных).

### 7) Границы ответственности модулей (P1)
**Junior+ умеет:** отделять orchestration от бизнес-логики и I/O.

- Что внедряем:
  - “тонкий” orchestrator, “толстые” pure-функции.
  - минимизация циклических импортов.

### 8) Минимальный quality gate в CI (P1)
**Junior+ умеет:** предотвращать регрессии до merge.

- Что внедряем:
  - шаги: lint + tests + smoke run.
  - fail при падении P0-checks.

### 9) Agentic-ready контуры (P2, на будущее)
**Junior+ умеет:** проектировать функции так, чтобы ими мог управлять агент.

- Что внедряем:
  - idempotent actions.
  - machine-readable outputs (JSON-сводки шагов).
  - строгие input/output контракты инструментов.

### 10) Портфолио упаковка (P1)
**Junior+ умеет:** показывать проект как инженерный продукт.

- Что внедряем:
  - README: architecture, quickstart, known limits.
  - примеры запусков + sample logs + roadmap.


### 11) Ревизия и гигиена документации заметок (P1)
**Junior+ умеет:** поддерживать рабочие заметки в актуальном и пригодном для ревью состоянии.

- Что внедряем:
  - единый формат заметок в `docs/` (цель, контекст, решения, next steps).
  - регулярный обзор заметок: удаление устаревшего, фиксация статуса задач.
  - связь заметок с кодом: ссылки на затронутые модули и сценарии запуска.

## Почему это подходит именно вашему проекту

Текущее состояние проекта указывает, что **первый фокус должен быть P0/P1**, а не оптимизации модели:

- В `main.py` много флагов запуска, ручных переключателей и смешение тестового/боевого сценария.
- В `main_functions.py` есть смесь orchestration + инфраструктуры + побочных эффектов.
- Есть точечные тесты в `modules/tests`, но отсутствует единый тестовый каркас вокруг P0-цепочки.

Это повышает риск “модель не сходится” из-за неуправляемых различий запуска, а не только из-за ML-гиперпараметров.

## Шаблон одной итерации (как будем работать)

1. Выбираем тему (из roadmap выше).
2. Я даю 2–3 участка кода-кандидата + вариант “выберите сами файлы”.
3. Делаю диагноз (3–7 рисков с метками P0/P1/P2).
4. Предлагаю 3 варианта вмешательства:
   - **Minimal patch** (быстро, безопасно),
   - **Medium refactor**,
   - **Rewrite slice** (локальное переписывание).
5. Вы выбираете вариант.
6. Делаем изменения + фиксируем портфолио-артефакт.
7. Добавляем **Industry note (de-facto alternatives)**:
   - 1 альтернативная распространенная практика,
   - почему в этой итерации выбран текущий вариант,
   - мини-пример альтернативы (2–6 строк кода/команды).

## Межчатовый протокол работы (чат-оркестратор + чаты-итерации)

Да, этот документ можно использовать как **единый ориентир между чатами**.

- **Чат-оркестратор (этот):**
  - поддерживает roadmap,
  - фиксирует решения по приоритетам,
  - обновляет статус итераций,
  - хранит правила взаимодействия и DoD-шаблоны.
- **Чат-итерация (новый чат под тему):**
  - выполняет конкретную тему,
  - делает диагноз по выбранным файлам,
  - предлагает 2–3 варианта вмешательства,
  - вносит минимальные изменения в код.

### Что сохраняется между чатами

- История конкретного чата в новый чат **не переносится автоматически**.
- Но содержимое репозитория доступно из любого нового чата, поэтому
  `docs/junior_plus_program.md` можно использовать как «контракт процесса».

### Где хранить заметки по итерациям

Рекомендуемый подход:

1. В этом файле хранить **только**:
   - общую программу,
   - статусы по итерациям,
   - правила процесса.
2. Для каждой итерации заводить отдельный файл:
   - `docs/iterations/iteration_01.md`, `iteration_02.md`, ...
   - внутри: цель, диагноз, выбранный вариант (minimal/medium/rewrite), DoD, результат, что дальше.

Это уменьшает «кашу» и дает чистый портфолио-след по эволюции проекта.

### Шаблон блока "Industry note" (обязателен в итерациях)

```md
### Industry note (de-facto alternatives)
- Выбранный подход в итерации: `<подход>`
- Альтернатива (de-facto): `<подход>`
- Почему не берем сейчас: `<краткая причина: сложность/срок/приоритет>`
- Мини-пример:
  ```
  <2–6 строк кода или команд>
  ```
```

Пример (для CLI):

```md
### Industry note (de-facto alternatives)
- Выбранный подход в итерации: `--mode train|update_data|serve`
- Альтернатива (de-facto): `subcommands` (`train`, `update_data`, `serve`)
- Почему не берем сейчас: ниже порог входа для первой итерации
- Мини-пример:
  ```bash
  py main.py train
  py main.py serve
  ```
```

### Статусы итераций (рекомендуемый формат)

- `0 - Baseline/Program: done`
- `1 - Reproducible run: planned`
- `2 - Config validation: planned`
- ...

Обновлять статусы после каждой завершенной итерации.

## Критерий прогресса до Junior+

К концу программы должны выполняться критерии:

- Проект запускается по документированному сценарию без ручного “тыканья” флагов.
- Любой запуск оставляет диагностируемый след (логи + конфиг + run metadata).
- Базовые P0-сценарии покрыты автотестами.
- Ошибки классифицированы, падения не “проглатываются”.
- Архитектура модулей понятна и объяснима на собеседовании.

## Практика синхронизации между чатами (Git)

Если новый чат «не видит» файл из текущего, почти всегда причина в разной ветке/контейнере.

Минимальный стартовый чек в новом чате:

```bash
pwd
git branch --show-current
git log --oneline -n 5
rg --files | rg 'docs/junior_plus_program\.md'
```

> Примечание: этот файл — про учебную программу. Детали разовой настройки Git/SSH специально не держим здесь, чтобы не размывать фокус.


### Рабочий протокол веток (договор)

- Базовая стабильная ветка: `main_branch`.
- Рабочая ветка текущей итерации: `feature/iteration-01-cli` (долгоживущая на время итерации).
- Временные ветки `codex/*` не используем как основное место разработки; после завершения работы их удаляем локально и на `origin`.

Рекомендуемый цикл:

```bash
git switch main_branch
git pull
git switch feature/iteration-01-cli
git pull
# работа, коммиты
git push
```

Завершение итерации:

```bash
git switch main_branch
git pull
git merge --no-ff feature/iteration-01-cli
# smoke checks
git push
```

### Быстрый протокол безопасной синхронизации (если есть локальные правки и ветка behind)

```bash
git stash push -u -m "wip before sync"
git pull --rebase origin <branch>
git stash pop
```

После `stash pop` обязательно проверить `git status` и разрешить конфликты, если они появились.
