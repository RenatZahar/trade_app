# AGENTS.md demo: рабочий протокол Codex для проекта

Статус: черновик v0.1.

Назначение: превратить общие договоренности с Codex в короткий проектный протокол, который позже можно перенести в корневой `AGENTS.md`.

Этот файл не является активной инструкцией для Codex, пока он лежит в `docs/`. Активным станет только файл `AGENTS.md` в корне проекта или в одной из рабочих директорий.

## Базовое правило

Codex сначала понимает контекст, затем выбирает режим работы, затем меняет файлы только настолько, насколько нужно для задачи.

Перед любой задачей агент должен:

- проверить наличие папки `docs` и релевантных файлов в ней;
- посмотреть текущее состояние worktree;
- не откатывать чужие незакоммиченные изменения;
- работать маленькими проверяемыми правками;
- после изменений сообщить, что изменено и как проверено.

## Классы задач

### Маленькая локальная задача

Примеры:

- формат логов;
- argparse;
- комментарии;
- документация;
- тесты на pure-функции;
- небольшая правка без риска для данных.

Режим: можно сразу делать минимальную правку после короткого осмотра контекста.

### Средняя инженерная задача

Примеры:

- изменение поведения модуля;
- добавление CLI-флага;
- небольшая переработка пайплайна;
- исправление ошибки с тестами.

Режим:

1. Осмотреть код и документы.
2. Коротко сформулировать текущее поведение.
3. Сделать scoped patch.
4. Запустить релевантные тесты или объяснить, почему они не запускались.

### Рискованная задача

Примеры:

- большие SQLite-таблицы;
- bulk-переносы;
- индексы;
- maintenance-скрипты;
- миграции;
- долгие операции, которые могут быть прерваны.

Режим: сначала design review альтернатив, затем рекомендация, затем ожидание выбора пользователя перед реализацией.

Обязательные альтернативы для сравнения:

- minimal patch;
- set-based SQL / production-oriented вариант;
- workaround / maintenance-вариант;
- долгосрочный архитектурный вариант, если уместен.

Сравнивать нужно по скорости, рискам, возможности прерывания и продолжения, влиянию на индексы, сложности поддержки и проверкам до/после.

Подробные правила: `docs/maintenance_guidelines.md`.

## Протокол эксперимента

Эксперимент нужен, когда неизвестно, какой подход лучше, а ошибка выбора может привести к дорогой переделке.

### Паспорт эксперимента

Перед кодом фиксируются:

- название эксперимента;
- цель;
- гипотеза;
- контекст;
- затронутые сущности: пайплайн, функции, таблицы, индексы, настройки, тесты;
- входные данные и примерный объем;
- критерии успеха;
- критерии остановки;
- ожидаемые проверки.

### Изоляция экспериментального кода

Все временные сущности должны быть явно помечены:

- файлы: `experimental*.py` или отдельный модуль `experimental/`;
- функции: суффикс `_experimental`;
- таблицы: префикс `experimental_`;
- CLI-флаги: явное указание experimental в имени или help-тексте;
- документация: отдельный раздел "Эксперимент".

Экспериментальный код не должен незаметно становиться частью боевого пайплайна.

### Сравнение подходов

Для каждого варианта фиксируются:

- что именно делает вариант;
- где есть full scan;
- где есть `GROUP BY` по большой таблице;
- где есть массовые `INSERT`, `DELETE`, `UPDATE`;
- какие индексы нужны;
- что будет при остановке процесса;
- можно ли безопасно повторить запуск;
- какие проверки нужны до и после;
- как меняется сложность поддержки.

Важный пример из проекта: физическое разделение `data_table` и `few_tx_wallets` оказалось дорогим и сложным в сопровождении. Более перспективный путь - хранить статистику по кошелькам и фильтровать рабочие запросы по этой статистике, а не массово переносить строки туда-обратно.

### Измерения

Для конкурирующих вариантов фиксируются:

- команда запуска;
- размер тестового набора;
- время выполнения;
- потребление памяти, если видно из логов;
- количество затронутых строк;
- состояние индексов до и после;
- результат проверок корректности.

Если одновременно делаются два пайплайна, соревнующиеся части выносятся из боевых файлов в experimental-код. Боевой пайплайн меняется только после выбора победившего подхода.

### Финальный вывод

В конце эксперимента документируется:

- рассмотренные варианты;
- плюсы и минусы каждого;
- итоговое решение;
- почему выбран именно этот вариант;
- какой технический долг остается;
- какие элементы кода были затронуты;
- какие проверки пройдены.

### Интеграция и уборка

После решения:

1. Перенести выбранный подход в боевой код маленькими правками.
2. Удалить или изолировать проигравший experimental-код.
3. Проверить, что в боевом пайплайне не осталось случайных зависимостей от `experimental_*`.
4. Удалять только то, что больше не нужно после фиксации вывода.
5. Обновить документацию и список проверок.

## Режимы работы агента

### Direct patch

Использовать для маленьких локальных задач. Агент сразу делает минимальную правку и проверяет ее.

### Discuss-plan-execute

Использовать для средних и крупных задач. Агент сначала объясняет понимание задачи, риски и план фаз, затем выполняет только согласованный объем.

### Propose/apply

Использовать для крупных изменений архитектуры или поведения:

- `propose`: создать proposal, design notes и tasks;
- `apply`: выполнить конкретный пункт tasks;
- `archive`: зафиксировать итог и закрыть временные артефакты.

### Review

Использовать, когда нужно найти риски без правок. Ревью должно начинаться с findings, а не с общего резюме.

### Retro

Использовать после крупной задачи или повторной ошибки агента. Агент должен предложить минимальное изменение в `AGENTS.md` или skill-инструкции, но не применять его без подтверждения.

## Что не делать

- Не переписывать большие файлы без необходимости.
- Не внедрять новую архитектуру без обсуждения.
- Не делать опасные DB-операции без design review.
- Не переносить experimental-код в production без финального вывода.
- Не менять `.env` и секреты.
- Не удалять чужие изменения из worktree.
- Не превращать каждую мелкую задачу в тяжелый spec-процесс.
