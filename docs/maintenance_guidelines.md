# Maintenance guidelines

## Назначение

Этот документ фиксирует инженерные правила для задач, где простое рабочее решение может оказаться слишком медленным или рискованным на реальном объеме данных.

Правило особенно важно для:
- больших SQLite-таблиц;
- bulk-переносов строк между таблицами;
- пересоздания индексов;
- maintenance-скриптов;
- миграций и массовых `INSERT` / `DELETE` / `UPDATE`;
- сценариев, которые могут выполняться часами и быть прерваны вручную.

## Базовое правило

Перед реализацией рискованной или долгой maintenance-задачи сначала нужен короткий design review.

Не стоит сразу внедрять первый рабочий вариант, если задача затрагивает большие данные или может привести к долгой блокирующей операции.

## Что должен включать design review

- Текущее состояние данных:
  - какие БД, таблицы и индексы затрагиваются;
  - какие таблицы считаются рабочими, а какие хранилищными;
  - можно ли безопасно читать/писать данные во время операции.
- 2-4 альтернативы реализации:
  - minimal patch;
  - set-based SQL / production-oriented вариант;
  - maintenance/workaround;
  - долгосрочный архитектурный вариант, если он уместен.
- Для каждого варианта:
  - какие операции выполняются;
  - где полный scan;
  - где `GROUP BY` по большой таблице;
  - где массовый `DELETE`, `INSERT` или `UPDATE`;
  - где создаются или удаляются индексы;
  - примерная сложность по времени и объему данных;
  - риски при прерывании;
  - можно ли продолжить после остановки;
  - какие проверки нужны до и после.
- Рекомендацию:
  - какой вариант выбран;
  - почему он лучше при текущих вводных;
  - какой более правильный вариант остается техническим долгом, если выбран быстрый патч.

## Отдельно отмечать дорогие операции

В design review явно помечать операции, которые могут быть дорогими на текущем объеме данных:

- `COUNT(*)` по очень большой таблице;
- `GROUP BY Wallet_id` по полной `data_table`;
- `DELETE` из большой рабочей таблицы;
- `INSERT INTO ... SELECT ...` на сотни миллионов строк;
- пересоздание индексов;
- `VACUUM`;
- дедупликация через `GROUP BY` по всем колонкам;
- перенос данных через Python row-by-row вместо SQL-side операции.

## Правила для переносов между `data_table` и `few_tx_wallets`

- `data_table` считается рабочей таблицей.
- `few_tx_wallets` считается хранилищной таблицей для низкоактивных кошельков.
- Индексы обязательны прежде всего для `data_table`.
- Индексы в `few_tx_wallets` не являются обязательными, если таблица используется как холодное хранилище.
- После старта массового переноса из `data_table` в `few_tx_wallets` БД находится в промежуточном состоянии.
- Для таких операций нужно заранее понимать:
  - безопасную точку остановки;
  - можно ли повторно запустить скрипт;
  - не начнет ли скрипт лишний обратный перенос;
  - как проверить итоговое состояние.

## Минимальные проверки до и после

Перед запуском:
- подтвердить, какие таблицы будут затронуты;
- проверить наличие нужных таблиц;
- понять текущее состояние флага `TXS_MOVED`;
- проверить, какие индексы есть в рабочей таблице;
- оценить, есть ли быстрый способ посчитать объем работы без полного скана.

После завершения:
- проверить наличие рабочих индексов в `data_table`;
- проверить ожидаемое состояние `TXS_MOVED`;
- проверить, что `data_table` и `few_tx_wallets` имеют совместимые схемы;
- проверить количество строк в затронутых таблицах, если это не требует чрезмерно дорогого полного скана;
- зафиксировать результат в логах/tracker.

## Связь с тестами

Для maintenance-сценариев нужны smoke-проверки, которые быстро подтверждают базовую готовность окружения:

- существуют ожидаемые таблицы;
- схемы совместимы;
- индексы в `data_table` присутствуют после сервисных сценариев;
- флаги состояния не противоречат фактическому разделению данных;
- тест не требует реальной полной БД, если цель проверки не integration/live.

## Связь с персонализацией Codex

Персонализация Codex задает стиль работы агента.

Этот документ хранит проектное правило и rationale. Он нужен, чтобы решение не зависело только от текущего чата или настроек агента.
