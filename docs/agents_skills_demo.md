# Codex agents and skills: исследовательская записка

Статус: черновик v0.1.

Назначение: систематизировать, как использовать `AGENTS.md`, Codex skills и похожие workflow-подходы в этом проекте без переусложнения процесса.

## Короткий вывод

Для проекта нужен не набор модных skills, а маленькая операционная система работы с агентом:

1. `AGENTS.md` в корне проекта - постоянные правила.
2. 2-3 repo-scoped skills - повторяемые рабочие процессы.
3. Легкий propose/apply-процесс - только для крупных изменений.
4. Ручная retro-практика - улучшать инструкции после реальных ошибок, но не позволять агенту переписывать их самовольно.

Официальная модель Codex подтверждает это разделение: `AGENTS.md` задает инструкции проекта, а skills упаковывают повторяемые workflow с инструкциями, ресурсами и опциональными скриптами.

## Термины

### AGENTS.md

Постоянные инструкции для Codex в репозитории или рабочей папке.

Использовать для правил, которые должны действовать почти всегда:

- как читать `docs`;
- как обращаться с незакоммиченными изменениями;
- когда нужен design review;
- какие тесты запускать;
- как оформлять результат.

Не использовать для длинных методичек и редких процессов. У `AGENTS.md` должен быть небольшой, жесткий и понятный набор правил.

### Skill

Повторяемый workflow для конкретного типа задач.

Codex skill - это папка с обязательным `SKILL.md` и опциональными `scripts/`, `references/`, `assets/`. В `SKILL.md` должны быть `name` и `description`; описание важно, потому что по нему Codex решает, когда skill применять.

Skills подходят для:

- ревью Python-модуля;
- безопасного design review для data pipeline;
- подготовки proposal/tasks;
- ретроспективы процесса;
- повторяемых проверок.

### Plugin

Пакет распространения skills и app-интеграций. Для текущего проекта пока не нужен. Сначала достаточно repo-local skills.

### Subagent

Отдельный агент для параллельной или независимой работы. Полезен для свежего ревью, но запускать его нужно только явно и для конкретной задачи.

### MCP

Подключение внешних источников и инструментов. Для текущей темы важно как механизм доступа к документации, GitHub и другим системам, но не заменяет `AGENTS.md` или skills.

## Что дают подходы из исходного исследования

| Подход | Суть | Польза для проекта | Риск | Практическая версия |
| --- | --- | --- | --- | --- |
| GSD | Обсудить -> распланировать -> выполнить по фазам | Снижает хаос в крупных задачах | Замедляет мелкие правки | `discuss-plan-execute` |
| Superpowers | Режимы работы: brainstorm, TDD, review, task splitting | Дает агенту правильный режим под задачу | Можно превратить в ритуал | 4-5 именованных режимов в `AGENTS.md` |
| OpenSpec | Сначала proposal/spec/tasks, потом код | Хорошо для архитектуры и рискованных изменений | Избыточен для багфиксов | Легкий `propose/apply` без тяжелой бюрократии |
| Meta-skill | Улучшение самих инструкций после ошибок | Помогает не повторять ошибки агента | Опасен при автоматической самоправке | Только ручная retro с подтверждением пользователя |

## Рекомендованный стек v0

### 1. Корневой AGENTS.md

Содержит:

- правило читать `docs`;
- правило не трогать чужие изменения;
- режимы задач;
- design review для SQLite, bulk, индексов и maintenance;
- протокол экспериментов;
- формат финального ответа.

Источник для будущего переноса: `docs/AGENTS_demo.md`.

### 2. Skill: discuss-plan-execute

Назначение: крупные или неоднозначные задачи.

Trigger:

- "обсуди";
- "спланируй";
- "исследовательская работа";
- "рефакторинг";
- "архитектура";
- "не редактируй сразу".

Inputs:

- цель;
- ограничения;
- файлы или модули;
- критерии готовности.

Outputs:

- понимание задачи;
- риски;
- план фаз;
- вопрос к пользователю, если без него опасно двигаться;
- после согласования - выполнение только выбранной фазы.

### 3. Skill: review-python-module

Назначение: ревью конкретного Python-кода без правок.

Trigger:

- "review";
- "посмотри на риски";
- "найди баги";
- "без изменений";
- "fresh review".

Outputs:

- findings по severity;
- ссылки на файлы и строки;
- тестовые пробелы;
- краткое резюме после findings.

### 4. Skill: data-pipeline-safety-check

Назначение: любые операции с большими данными, SQLite, bulk-переносами, индексами, maintenance.

Trigger:

- `SQLite`;
- `bulk`;
- `data_table`;
- `few_tx_wallets`;
- `wallet_stats`;
- `moving_txs`;
- `VACUUM`;
- `ANALYZE`;
- `индекс`;
- `maintenance`.

Outputs:

- текущее состояние данных;
- 2-4 альтернативы;
- дорогие операции;
- риск остановки;
- возможность повторного запуска;
- проверки до/после;
- рекомендация без реализации, пока пользователь не выбрал подход.

### 5. Skill: skills-retro

Назначение: обновлять правила после крупных задач и повторных ошибок.

Trigger:

- "ретро";
- "что улучшить в AGENTS";
- "агент снова ошибся";
- "обнови инструкции".

Правило безопасности: skill может предложить patch к инструкциям, но не должен применять его без явного подтверждения.

## Skill Contract v0

Каждый skill должен описывать:

```md
---
name: skill-name
description: When to use this skill. Include trigger words and boundaries.
---

# Goal

What this skill helps Codex do.

## Use When

- Concrete trigger 1.
- Concrete trigger 2.

## Do Not Use When

- Boundary 1.
- Boundary 2.

## Inputs

- Required input.
- Optional input.

## Workflow

1. Step.
2. Step.
3. Step.

## Outputs

- Expected artifact.
- Expected summary.

## Failure Policy

What to do when context is missing, risky, or contradictory.
```

## Где хранить

Для проекта:

```text
.agents/
  skills/
    discuss-plan-execute/
      SKILL.md
    review-python-module/
      SKILL.md
    data-pipeline-safety-check/
      SKILL.md
    skills-retro/
      SKILL.md
```

Пока skills экспериментальные, лучше держать их в `docs` как дизайн. Когда формулировки стабилизируются, переносить в `.agents/skills`.

## Propose/apply для крупных изменений

Легкая структура:

```text
docs/
  changes/
    change-name/
      proposal.md
      design.md
      tasks.md
      result.md
```

### propose

Создает:

- зачем меняем;
- что входит в scope;
- что не входит;
- альтернативы;
- риски;
- tasks.

Ничего не меняет в production-коде.

### apply

Выполняет один или несколько согласованных пунктов `tasks.md`.

После выполнения:

- отмечает выполненные пункты;
- фиксирует проверки;
- пишет, что осталось.

### archive

После завершения:

- переносит выводы в постоянные docs;
- удаляет временный experimental-код;
- оставляет `result.md` с итогом.

## Правила против переусложнения

- Не делать spec для правки на 5 строк.
- Не создавать skill, если процесс еще не повторился хотя бы 2-3 раза.
- Не держать больше 3-4 активных repo skills на старте.
- Не смешивать постоянные правила и длинные методички в одном `AGENTS.md`.
- Не разрешать meta-skill автоматически менять инструкции.
- Не использовать subagent там, где обычное локальное ревью достаточно.

## Связь с текущими документами проекта

- `docs/AGENTS_demo.md` - будущий рабочий протокол агента.
- `docs/maintenance_guidelines.md` - уже готовая основа для `data-pipeline-safety-check`.
- `docs/junior_plus_program.md` - общий процесс итераций и quality gate.
- `docs/iterations/` - история решений; сюда можно добавлять результаты крупных experiments.
- `docs/main_notes.md` - backlog и технические заметки, которые могут становиться propose/apply-задачами.

## Предлагаемый план внедрения

1. Утвердить `docs/AGENTS_demo.md` как основу.
2. Перенести короткую версию в корневой `AGENTS.md`.
3. Создать первый skill `data-pipeline-safety-check`, потому что он закрывает самый дорогой риск проекта.
4. Создать `review-python-module`.
5. Создать `discuss-plan-execute`, если крупные задачи регулярно требуют фазового плана.
6. Ввести `skills-retro` только после 2-3 реальных итераций.
