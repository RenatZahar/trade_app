# Agents and skills: русское пояснение

Статус: рабочее пояснение для человека.

Этот файл не является активной инструкцией для Codex. Активные правила лежат в корневом `AGENTS.md`, а повторяемые workflow лежат в `.agents/skills/*/SKILL.md`.

## Что оформлено сейчас

В проект добавлены:

- `AGENTS.md` - короткие постоянные правила проекта для Codex;
- `.agents/skills/data-pipeline-safety-check/SKILL.md` - обязательный safety workflow для SQLite, больших данных, индексов и maintenance;
- `.agents/skills/discuss-plan-execute/SKILL.md` - workflow для крупных, неоднозначных и исследовательских задач;
- `.agents/skills/review-python-module/SKILL.md` - workflow для ревью Python-кода без правок;
- `docs/agents_skills_translate_ru.md` - этот человеческий перевод/rationale.

Старый `docs/AGENTS_demo.md` удален, потому что его роль перешла к настоящему корневому `AGENTS.md`.

## Роли файлов

### `AGENTS.md`

Это активный контракт для агента.

Туда входят только правила, которые должны срабатывать часто:

- сначала читать `docs`;
- не откатывать чужие изменения;
- отличать маленькие задачи от больших;
- делать design review перед рискованными DB/maintenance изменениями;
- использовать экспериментальные префиксы;
- запускать релевантные проверки.

В `AGENTS.md` не нужно держать длинный русский перевод. Лишний текст может размывать обязательные инструкции.

### `.agents/skills/*/SKILL.md`

Это активные repo-scoped skills. Codex видит их как отдельные workflow и может применять явно или по описанию.

Сейчас созданы три skill:

1. `data-pipeline-safety-check` - главный обязательный skill для опасных данных.
2. `discuss-plan-execute` - способ не начинать крупную задачу с кода.
3. `review-python-module` - зафиксирован заранее, чтобы не забыть режим ревью без правок.

### `docs/agents_skills_translate_ru.md`

Это пояснение для тебя: зачем эти файлы нужны, что куда положено, и что можно развивать позже.

## Почему `data-pipeline-safety-check` обязателен

В проекте уже был дорогой опыт с физическим разделением `data_table` и `few_tx_wallets`. Массовые переносы строк, индексы, `VACUUM`, `ANALYZE` и большие SQLite-таблицы могут стоить много часов и приводить к промежуточным состояниям.

Поэтому правило жесткое:

- если задача только читает информацию безопасными запросами, агент может работать без отдельного подтверждения;
- если задача меняет БД, индексы, maintenance-скрипты или может запустить дорогой scan, сначала нужен design review альтернатив;
- после design review агент рекомендует вариант и ждет выбора пользователя.

## Зачем `discuss-plan-execute`

Это проектная версия режима "сначала понять, потом делать".

Использовать для:

- архитектуры;
- рефакторинга;
- исследовательских задач;
- задач с несколькими фазами;
- случаев, когда непонятно, где граница безопасного изменения.

Для маленьких локальных правок этот режим не нужен.

## Зачем `review-python-module`

Это режим "найди риски, но не редактируй".

Он пригодится для:

- ревью конкретного файла;
- ревью patch/diff;
- поиска поведенческих регрессий;
- проверки тестовых пробелов;
- независимого взгляда перед merge.

Пока он не обязан срабатывать постоянно, но теперь он оформлен и не потеряется.

## Что не включено сейчас

### `skills-retro`

Идея полезная, но рискованная. Агент не должен сам переписывать свои инструкции в фоне.

Правильная версия:

1. После повторной ошибки агент предлагает минимальное изменение `AGENTS.md` или skill.
2. Пользователь подтверждает или отклоняет.
3. Только после подтверждения инструкция меняется.

Пока это правило записано в `AGENTS.md`, но отдельный active skill не создан.

### Heavy OpenSpec

Полный процесс `proposal/spec/tasks/archive` пока не обязателен. Его можно добавить позже, если крупные изменения начнут повторяться.

## Roadmap

Ближайший рабочий порядок:

1. Использовать новый `AGENTS.md` в реальных задачах.
2. Проверить, что `$data-pipeline-safety-check` срабатывает на DB/maintenance запросах.
3. Проверить, что `$discuss-plan-execute` помогает в крупных задачах и не мешает маленьким.
4. Использовать `$review-python-module` перед сложными merge/refactor.
5. После 2-3 реальных ошибок вернуться к идее `skills-retro`.
