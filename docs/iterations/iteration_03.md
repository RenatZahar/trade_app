# Iteration 03

## Тема

Logging and observability of pipeline

## Цель итерации

Сделать запуск пайплайна и сервисных сценариев диагностируемым:
- видеть старт и завершение run;
- видеть ключевые stage-и и их длительность;
- собирать обычные operational logs и tracker-события в один поток;
- не плодить отдельные лог-файлы на каждый модуль.

## Текущее решение

- Логирование переведено в один лог-файл на один run.
- Используется единый logger `"app"`.
- Модули больше не создают собственные файловые логгеры, а получают общий logger через `logging.getLogger("app")`.
- Для записи логов используется один queue-backed поток:
  - `QueueHandler`
  - `QueueListener`
  - запись в `logs/<run_id>.log`
- `RunTracker` отделен от logging-слоя:
  - tracker хранит состояние run и stages;
  - logger пишет события на основе состояния tracker.

## Формат наблюдаемости

- Обычные operational logs остаются обычными `logger.info(...)` / `logger.error(...)`.
- Для lifecycle-событий используется префикс `_TRACKER_INFO`.
- Договор tracker-событий:
  - `run_started` используется один раз в начале run;
  - `run_finished` используется один раз в конце run;
  - конец run с ошибкой и ручное прерывание тоже считаются `run_finished`, а различие хранится в `status`;
  - `stage_started` / `stage_finished` используются только для важных этапов сценария;
  - бытовые operational messages не должны оборачиваться в tracker.
- Сейчас `_TRACKER_INFO` применяется для:
  - `run_started`
  - `run_finished`
  - `stage_started`
  - `stage_finished`

Пример текущего потока:

```text
2026-04-04 17:43:53,119 [INFO] [app] _TRACKER_INFO event=run_started run_id=11 status=running start_arg=start_parser, True started_at=2026-04-04 17:43:53 finished_at=None duration_sec=None duration_human=None error=None
2026-04-04 17:43:54,516 [INFO] [app] Старт mf.btc_status_monitor
2026-04-04 17:43:55,033 [INFO] [app] Redis успешно запущен и работает.
2026-04-04 17:44:00,224 [ERROR] [app] Ошибка при доступе к базе данных: unable to open database file
```

## Принятые решения

- Не логировать через tracker каждый бытовой message.
- Обычные события уровня "Redis успешно запущен" оставлять в обычных логах.
- Tracker использовать только для опорных точек расследования:
  - старт run;
  - завершение run;
  - ключевые stage-и.
- Ошибка run и ручное прерывание не выделяются в отдельные tracker-event names; они выражаются через `run_finished` + `status=error|interrupted`.
- JSON summary-файлы `run_<id>.json` на текущем этапе убраны как лишний слой.

## Что пока устраивает

- Текущий формат `_TRACKER_INFO` достаточно читаемый для ручного тестирования.
- Финальную шлифовку формата пока не делаем заранее.
- Уточнение формата оставляем на этап реальных прогонов и расследований.

## Что пока не фиксируем окончательно

- Финальный формат `_TRACKER_INFO`.
- Полный обязательный набор stage-ов для всех сценариев.
- Точный lifecycle parser в фоне:
  - когда run считать `running`;
  - когда считать `finished`;
  - когда считать `failed`, если работа уходит в поток.

Это переносится на следующий этап шлифовки модулей.

## Промежуточный вывод

- Единый поток логов на run оказался удобнее, чем отдельные лог-файлы по модулям.
- Разделение ответственности между tracker и logger стало понятнее:
  - tracker хранит состояние;
  - logger пишет события.
- База для дальнейшей observability уже есть; дальше важнее не расширять инфраструктуру, а аккуратно доводить lifecycle конкретных модулей.

## Минимальный договор tracker на текущем этапе

- Tracker нужен для новых вех выполнения, а не для всех сообщений подряд.
- Обязательные точки:
  - старт run;
  - финиш run;
  - важные stage-и скрипта.
- Важные stage-и сейчас понимаются как смысловые шаги сценария:
  - parser: подготовка списка блоков, обработка группы блоков;
  - training flow: подготовка correlation data, training, evaluate, save artifact.
- Не считаем stage-ами:
  - старт Redis;
  - запуск monitor thread;
  - прочие бытовые технические сообщения, которые и так достаточно видны в обычных логах.

## Ручная проверка

- Прогнаны два сценария:
  - `run_id=12`: `--start_parser`
  - `run_id=13`: `--test right_now_test`
- `run_id=13` выглядит как ожидаемый happy path:
  - есть `run_started`;
  - есть `run_finished`;
  - статус `success`;
  - duration записан корректно.
- `run_id=12` показал, что logging-слой в целом работает, но parser-сценарий еще не доведен до финального договора:
  - в логе все еще видны старые tracker-stage вокруг Redis и monitor start;
  - финальное событие записано как `run_interrupted`;
  - это означает, что parser lifecycle и cleanup tracker-событий еще требуют отдельной шлифовки.

## Решение по закрытию итерации

- Основная цель итерации достигнута:
  - единый лог-файл на run работает;
  - queue-backed logging работает;
  - `_TRACKER_INFO` для run/stage lifecycle внедрен;
  - happy path уже читается осмысленно.
- Остаточный хвост не блокирует закрытие `iteration_03`, потому что относится не к core outcome итерации, а к локальной шлифовке конкретных модулей.
- Эти хвосты переносятся в последующую модульную доработку:
  - дочистить parser-сценарий под согласованный tracker-договор;
  - добить финальную чистоту stage-набора;
  - уточнить lifecycle long-running parser-сценария на границе `main.py` / `main_functions.py` / `modules/blockchain_parser/*`.

## Статус

- `iteration_03` считается закрытой по основному DoD.
- Остаточная шлифовка parser/monitor lifecycle зафиксирована как отдельный модульный хвост и может выполняться вне рамки самой итерации.
