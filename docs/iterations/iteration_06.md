# Iteration 06 - SQL state recovery and runtime stabilization

## Тема

Стабилизация состояния БД и runtime после закрытия тестового фундамента.

## Статус

Planned

## Контекст

- `iteration_05` закрыла базовый pytest/smoke/integration-live контур.
- В процессе maintenance стало ясно, что физическое разнесение строк между
  `data_table` и `few_tx_wallets` слишком дорого на текущем объеме данных.
- Запущен сценарий `move_txs_back`, который возвращает строки из `few_tx_wallets`
  обратно в `data_table`.
- Текущий `moving_txs` остается legacy-сценарием до проектирования новой модели
  `data_table + wallet_stats`.

## Цель итерации

Вернуть проект в устойчивое рабочее состояние перед следующими крупными
изменениями:

- все транзакционные строки собраны в `data_table`;
- служебные таблицы bulk-переносов очищены;
- рабочие индексы восстановлены;
- `VACUUM` и `ANALYZE` выполнены после возврата данных;
- smoke-тесты дают быстрый зеленый сигнал;
- дальнейшие SQL-изменения вынесены в осознанный design review.

## Что нужно сделать

### 1. Дождаться завершения `move_txs_back`

- Проверить, что сценарий завершился штатно.
- Убедиться, что в логах/tracker есть финальное сообщение о завершении.
- Если сценарий был прерван, повторно запустить его: перенос батчевый и должен
  продолжить с оставшихся строк в `few_tx_wallets`.

### 2. Проверить итоговое состояние БД

- `TXS_MOVED = False`.
- `few_tx_wallets` пустая или содержит только ожидаемый остаток, если он будет
  отдельно объяснен.
- `data_table` содержит рабочий набор строк.
- Служебные таблицы вида `service_*`, созданные для move/rebuild-подходов,
  удалены.
- WAL/SHM файлы не разрастаются после завершения maintenance.

### 3. Проверить рабочие индексы

Ожидаемые индексы `data_table`:

- `idx_wallet_id`
- `idx_block_height`
- `idx_txs_blocktime`
- `idx_block_height_wallet_id`

Индексы в `few_tx_wallets` не считаются обязательными, если таблица больше не
используется как активная часть рабочего пайплайна.

### 4. Зафиксировать результат через тесты

Быстрый smoke/regression контур:

```powershell
python -m pytest tests\unit_smoke -q
```

Live-тесты не являются обязательными для каждого локального изменения, но после
стабилизации БД стоит отдельно прогнать baseline-сценарий:

```powershell
python main.py test downloaded-from-btc-data 3 1
```

### 5. Не развивать legacy `moving_txs` дальше без design review

`moving_txs` не удаляется сразу, но новые решения по фильтрации low-tx кошельков
нужно проектировать вокруг модели:

- `data_table` хранит все строки транзакций;
- `wallet_stats` или аналогичная таблица хранит классификацию кошельков;
- pipeline фильтрует данные через `JOIN` / `EXISTS`, а не через физический
  перенос сотен миллионов строк.

## Границы итерации

В этой итерации не делаем:

- сравнение current pipeline со старым notebook-flow;
- actor-level объединение кошельков;
- массовый пересчет `Btc_block_time_price`;
- полную переработку модели данных под `wallet_stats`.

Эти задачи остаются в `iteration_12`.

## Definition of Done

- `move_txs_back` завершен или явно зафиксирован как возобновляемый процесс.
- `TXS_MOVED = False`.
- Service-таблицы bulk-переносов очищены.
- Обязательные индексы `data_table` присутствуют.
- `VACUUM` выполнен после возврата данных.
- `ANALYZE` выполнен после `VACUUM`.
- `python -m pytest tests\unit_smoke -q` проходит.
- В документах зафиксировано, что физический `moving_txs` является legacy-путем.
