# Iteration 02

## Тема

Configuration without magic

## Цель итерации

Сделать конфигурацию проекта более явной и предсказуемой:
- отделить runtime/env-настройки от путей проекта;
- вынести модульные настройки в `settings/*`;
- убрать зависимость проекта от старого центрального `config.py`;
- сократить "магические" импорты и ручное вмешательство в `sys.path`.

## Затронутые темы

- `settings/runtime.py`
- `settings/paths.py`
- `settings/parser.py`
- `settings/price_peaks.py`
- `settings/sql.py`
- `settings/data_operations.py`
- перенос импортов со старого `config.py`
- отказ от `sys.path.append(...)`

## Краткая теория

- `.env` хранит внешние значения среды и machine-specific настройки.
- `runtime` читает `.env` и задает контракт среды выполнения.
- `paths` хранит внутренние пути проекта.
- `settings/<module>.py` хранит domain/module-specific параметры.

Главная идея итерации: делить конфигурацию не "по привычке", а по ответственности.

## Диагноз до изменений

- Конфигурация была размазана между корневым `config.py`, локальными модульными конфигами и прямыми вызовами `os.getenv()`.
- В проекте использовались ручные `sys.path.append(...)`, что добавляло import-магии.
- В одном слое были смешаны:
  - env/runtime-настройки,
  - пути проекта,
  - параметры алгоритмов и обучения.
- Ошибки в конфигурации были трудно локализуемы, потому что источник значений был неочевиден.

## Что сделано

- Создан слой `settings/`.
- Runtime/env-настройки вынесены в `settings/runtime.py`.
- Пути проекта вынесены в `settings/paths.py`.
- Настройки парсера вынесены в `settings/parser.py`.
- Настройки поиска пиков вынесены в `settings/price_peaks.py`.
- SQL-настройки вынесены в `settings/sql.py`.
- Настройки data operations вынесены в `settings/data_operations.py`.
- Активные импорты `from config import ...` переведены на `settings.*`.
- Убраны ручные `sys.path.append(...)`.
- Имя parquet-файла очищенных цен больше не хранится в `paths.py`, а собирается рядом с использованием.

## Результат

- Конфигурация стала структурно понятнее.
- Источники настроек разделены по слоям.
- Импортный слой проекта больше не зависит от старого `config.py`.
- Проект компилируется на уровне `python -m compileall`.

## Что проверить при тестировании

- Проверить создание файла очищенных цен с корректным именем:
  - формат имени должен соответствовать `smoothed_BTCUSDT_<N>min.parquet`;
  - имя должно использовать актуальное значение `line_time_duration_min`;
  - путь и имя должны совпадать между модулем очистки цен и модулем поиска пиков.
- Проверить чтение этого файла в `update_peaks()`.
- Проверить базовые сценарии запуска:
  - parser,
  - flask,
  - main pipeline.

## Остаточные замечания

- Итерация закрывает основной конфигурационный рефакторинг, но полноценная runtime-проверка всех сценариев запуска должна быть выполнена отдельно.
- Особое внимание при тестировании уделить генерации и чтению parquet-файла очищенных цен.

## DoD

- Есть отдельный слой `settings/`.
- Runtime и project paths разделены.
- Модульные настройки вынесены по смыслу.
- Активные импорты из старого `config.py` убраны.
- Убрана import-магия через `sys.path.append(...)`.
- Итог итерации зафиксирован в `docs/iterations/iteration_02.md`.

## Industry note (de-facto alternatives)

- Выбранный подход в итерации: плоский слой `settings/*` с разделением по ответственности.
- Альтернатива (de-facto): типизированный settings-слой через `pydantic-settings` или dataclass-объекты конфигурации.
- Почему не берем сейчас: для текущего проекта важнее сначала убрать магию и стабилизировать структуру, чем усложнять слой конфигурации типизацией.
- Мини-пример:
  ```python
  from pydantic_settings import BaseSettings

  class RuntimeSettings(BaseSettings):
      rpc_user: str
      rpc_password: str
  ```
